# プリプロセス命令仕様

Erq ではパーサーが生成した SQL 文字列中に、ヌル文字 (`\u0000`) で囲まれた「プリプロセス命令」を埋め込みます。`src/eval-utils.js` の `preprocess` がこれらを解釈して実行時に SQL を動的に書き換えます。本書では現行実装で利用されている命令と、それらがどのように解決されるかをまとめます。

## 命令フォーマット

```
\0<type><payload>\0
```

- `type`: 1 文字の識別子。`v`, `t`, `e`, `c` など。
- `payload`: ヌル文字以外の任意の文字列。多くの場合 JSON 文字列や式が入る。

`preprocess` はクエリ 1 本につき 1 度実行され、命令を置換した最終的な SQL を返します。毎回実行される前に相関用キャッシュをクリアするため、直前に行われた DDL 変更にも追従します。

## サポートされる命令

### `\0v<name>\0` — 変数展開

- 役割: `@foo` のような DSL 変数参照を SQL リテラルに置換する。
- 処理:
  1. `payload` から `env` マップを引いて値を取得 (`env` は `Map<string,string>`）。
  2. 見つからない場合は例外を投げる。
  3. 取得した文字列をそのまま挿入する。

### `\0t<payload>\0` — テーブル参照の解決

- 役割: DSL のテーブル名／変数から実際の SQLite テーブル名を導出する。
- `payload` には以下のいずれかが入る:
  - 文字列リテラル … そのまま返す。
  - `["schema", "@var"]` のような JSON 配列 … 変数を展開してから `schema.\`table\`` の形式に整える。
  - `@var` … 変数展開後に識別子として引用する。

SQLite の予約語や記号を含む場合は `quoteSQLName` を通じて適切にエスケープされます。

### `\0e<sql>\0` — 式の評価

- 役割: `select` 式を 1 行 1 列で評価し、結果をクエリ文字列へ直接挿入する。
- 処理:
  1. `payload` をそのまま SQL として `prepare` → `pluck().get()`。
  2. 実行時のバインド値として `env` の内容を利用する (`Object.fromEntries(env.entries())`)。
  3. 得られた値を文字列化して挿入。

### `\0c<payload>\0` — 自動相関制約 (automatic correlation context propagation)

この命令は `^table` 構文から生成される関連条件を、外部キー定義に基づいて埋め込む用途に特化しています。`payload` は JSON で、以下の 2 形式のいずれかになります。

```
[
  [<parent-context>, ...],   // 複数親テーブルがある場合
  <target-context>
]

または

[
  <single-parent-context>,   // 親テーブルが 1 つの場合
  <target-context>
]
```

ここで各コンテキストは `[schema|null, table, alias]` の 3 要素配列です。`schema` が省略されている場合は `pragma_table_list` を用いて補完します。

処理手順:

1. `payload` を JSON としてパースし、親側コンテキストを配列に正規化する。
2. 親テーブルそれぞれについて `buildPredicateForContext` を呼ぶ。
   - `pragma_foreign_key_list(child [, schema])` を用いて外部キー候補を取得。
   - 子→親の外部キーが存在しなければ、親→子の向きでも検索。
   - 一意に決まらない場合は例外。
   - 主キー／外部キーが複数列のときは `(a, b) = (c, d)` の形に展開。
3. 得られた述語を `and` で連結して返す。親側で関連する外部キーが 1 つも見つからない場合はエラー。

この命令は join などで複数の親テーブルが存在するときも対応できるよう設計しており、`TableBuilder` が保持している「現在のテーブルコンテキスト」配列をそのまま渡しています。コンテキストはサブクエリへ入るたびに引き継がれ、別名 (`as ...`) を挟んだ場合も alias 情報が利用されます。

## 自動相関コンテキストの流れ

1. パーサーは `^table` を検出すると `\0^[...] \0` という中間命令を埋め込みます。
2. `TableBuilder` はクエリ構築時に中間命令を `\0c[...] \0` へ置換する。このとき、保持している親テーブルのコンテキスト配列を JSON に含めます。
3. `preprocess` が `c` 命令を解釈し、上記の手順で外部キー制約に展開します。

この仕組みにより、`p join q { exists ^r }` のような DSL でも `r` と `p` / `q` の両方について外部キーを調べ、必要な等式を自動的に生成します。

## エラーハンドリング

- 不正な JSON など `payload` が想定外の場合は `Error` を送出する。
- `c` 命令の外部キー探索で該当が見つからない場合、または複数ヒットした場合は例外を投げて呼び出し元に伝える。
- `e` 命令の SQL 実行でエラーが発生した場合も例外で停止する。

## 今後の拡張ポイント

- 外部キー探索に利用しているキャッシュ (`correlationCache`) は `preprocess` のたびにクリアしているが、必要に応じて `schema_version` などを用いた賢いキャッシュが追加できる。
- 新しいプリプロセス命令を追加する場合は、ここで紹介した形式に従い、`switch` 文へ処理を追加する。
